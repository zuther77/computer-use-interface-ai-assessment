# Design Write-Up — Computer-Use Automation System

## 1. Architecture

The system is a Python package (`bankops/`) with five layers, each depending only on the layer below it: **perception** (turns a live page into an indexed list of interactive elements with fallback locators), **action tools** (typed, single-purpose calls — `click`, `type_text`, `select_option`, `navigate`, `extract`, `remember`, `observe`, `finish`, `report_stuck`), **discovery loop** (observe → decide → act against GLM-5.2 via the OpenAI SDK, structured working state rather than full transcript replay), **artifact/recorder** (distills a successful run into a typed, versioned capability), and **replay engine** (executes a saved artifact deterministically, no LLM involved). Safety (allowlist, risk tags, redaction) and escalation (intervention requests, handoff) sit alongside all layers rather than inside any one of them, since both need to intercept execution at multiple points.

Target surface: **ParaBank**, self-hosted via Docker — a real (if dated) banking application with native multi-step flows (login, account lookup, fund transfer, bill pay) and genuine business-rule errors (insufficient funds, invalid login, not-found lookups), avoiding the reproducibility and rate-limit risk of the public hosted instance while still exercising a legacy, non-trivial surface.

Key trade-off: the LLM provider (GLM-5.2, via the OpenAI-compatible SDK with swappable `base_url`/`api_key`) was chosen over a premium closed model on cost grounds, but only after checking published agentic tool-calling benchmarks — a cheaper open-weight model with unreliable structured tool-calling would have compromised the one property this loop depends on most: emitting one well-formed action per step without corrupting the recording.

## 2. Artifact schema

An artifact is a flat, ordered list of typed steps — not a branching graph. This mirrors what a single real discovery run actually produces (per the assignment's own framing that one successful run is sufficient), and pushes all error/outcome handling into the *replay engine* rather than into artifact structure, keeping the schema honest to a real recording rather than a hypothesized set of paths.

Each step carries:
- **An ordered list of candidate locators**, each tagged by strategy (`role_name`, `id_attribute`, `text_content`, `css_structural`), tried in priority order at replay time until exactly one visible/enabled element resolves. This is the direct answer to "how each target element is identified, with reasoning about robustness" — role/accessible-name is trusted most (closest to how a human identifies a control, most resistant to incidental markup changes), raw structural CSS is the last resort.
- **Typed input parameters**, auto-promoted from any `type_text`/`select_option` value at recording time (parameter name derived from the element's accessible label), with an optional `is_constant` override for the rare case a recorded value should stay fixed rather than become a caller-supplied argument.
- **Typed output fields**, populated only from deliberate `extract` actions — kept distinct from `remember` (working memory used mid-run, never exposed to the caller), so the schema cleanly separates "what this capability returns" from "what it needed to keep track of internally."
- **A per-step signature** (URL + a stable page-identity marker, captured automatically as an observation byproduct) plus one deliberate terminal checkpoint tied to the goal — giving precise mid-flow failure localization rather than a single pass/fail read at the very end. Two checkpoint fields exist specifically because live replays got wrong answers without them: `allowed_error_messages` (error-classed page text observed on the *recorded* path is tolerated; any *unrecorded* one means the step did not land in the recorded state — this caught a swapped date-range search that "succeeded" while the page read `Invalid date format`) and `required_locator` (a goal-tied element that must be present — this caught a silently empty result set, and ParaBank's asynchronously rendered loan decision, where URL and heading never change).
- **A `risk_level` tag** (`read_only` / `state_changing_reversible` / `state_changing_irreversible`), set manually at authoring time, with irreversible artifacts additionally flagging their point-of-no-return step.

The schema is a Pydantic model serialized to plain JSON with a `schema_version` field — reviewable directly by a human, git-diffable per revision, with no separate versioning infrastructure needed.

## 3. Determinism & error handling

Replay never invokes the LLM. Each step's locator candidates are tried in priority order (first unique visible/enabled match wins); Playwright's built-in auto-wait handles short-lived actionability, layered with an explicit tiered retry/backoff specifically for "locator not found yet" conditions — giving "transient slowness" its own handling path rather than collapsing it into a generic timeout. Caller-supplied parameters are validated against the artifact's typed input schema *before* any browser interaction begins, so a bad argument fails cleanly at the boundary rather than surfacing several steps into the UI as a confusing mid-flow error.

The result contract is a discriminated union of three typed outcomes:
- **`SuccessResult`** — the declared typed outputs.
- **`BusinessOutcomeResult`** — a named, legitimate non-happy-path result (e.g. insufficient funds, member not found), detected via **recorded outcome signatures**: alongside the primary checkpoint, a step can carry additional known-alternate-outcome signatures (locator + expected text pattern), captured via a deliberate secondary discovery/exploration run against the live app and merged into the artifact. This treats "no such member" as a first-class, versioned, reviewable fact about the capability — not a runtime guess.
- **`FailureResult`** — step index, what was expected, what was observed (with the run's evidence folder filed alongside) — for anything that resolves to neither a business outcome nor success.

The moment any step resolves to a business outcome or hard failure, replay stops immediately — it does not continue executing steps against a page in a state the artifact was never designed for, which matters specifically because some of these steps are financial and not all outcomes are safely reversible.

**Known, deliberate cut on UI drift:** replay stops at the first candidate locator that resolves — and *does* log which strategy tier won (that is Section 4's drift signal, present in every step log) — but it does not go on to evaluate the remaining candidates to detect non-primary matches. Doing so would give free secondary drift visibility at negligible extra runtime cost; cut here for simplicity, documented in Section 7.

## 4. Heterogeneity & multi-tenant

**Surface abstraction.** Perception and action execution already interact with the rest of the system only through two shapes: "return an indexed list of elements with candidate locators" and "execute this typed action against a locator." A legacy web surface (framesets, non-semantic tables) would be a new adapter implementing the same interface, adding new locator-strategy tags (e.g. a table-cell-position or frame-scoped strategy) to the existing tagged-candidate list. A desktop surface would be a new adapter over OS accessibility APIs, producing the same "indexed elements + candidates" shape with an `automation_id`-style tag. In both cases the artifact schema, replay engine, and error taxonomy are untouched — they operate on the adapter's output shape, not on browser DOM specifics. This isn't a hypothetical extensibility claim; it's a description of a seam that already exists in the implemented design.

**Multi-tenant reuse.** One canonical base artifact per capability, plus an optional, sparse per-tenant override — a small diff replacing only what differs (a locator candidate, a route segment, a label string), not a parallel artifact. Most tenants running the same underlying vendor product would need no override at all for most steps. Drift detection reuses data already produced for the structured log: each step's log entry records which locator-strategy tier actually resolved; a tenant whose replays start falling back to lower-priority strategies (or failing outright) at a materially higher rate than others is a concrete, measurable signal with zero new instrumentation. Where a tenant's customization is too large to express as a small override, the honest answer is a newly-recorded base artifact for that variant, not a forced-fit diff — this boundary is a design choice, not an oversight.

## 5. Escalation & handoff

Two events can trigger escalation: `report_stuck` from the discovery loop, or a `FailureResult` from replay. Either raises a structured `InterventionRequest` (run/artifact reference, step index, reason, screenshot, observation snapshot, timestamp), persisted immediately to disk — the notification channel itself (how a human is alerted) is stubbed as a log line, since a real routing/ticketing integration is explicitly out of scope, but the request object is real and complete, not a placeholder.

Runs are headless by default; the handoff path runs the browser headed (`--headed`) locally. On escalation, the automation loop simply stops issuing commands — it does not tear down the session — while a human operates the same visible, live Playwright-controlled window directly. The "operator console" is the raw browser window itself: bare, but genuinely functional, matching the assignment's own calibration for this scope ("even a bare/mock operator surface... make the handoff mechanism and control-transfer model real"). A headless escalation still persists the complete intervention request — there is simply no operator surface to pause on.

On resume, automation does not blindly continue from where it paused. It re-observes the current page and, for a replay in progress, verifies the next step's expected checkpoint against what it actually sees — a mismatch raises a *new* intervention rather than guessing and risking an action against an unexpected state. For a *discovery* in progress, a resume signal does one better than releasing the pause: the loop continues its normal per-step cycle from the human's state — its first act is to re-observe, so whatever the human fixed in the browser becomes the model's next input, with action history and evidence step numbering carried over (bounded to three pause/resume cycles per run). The first implementation recorded the decision and simply ended the run; a live handoff — a human resolved a bad-credentials stop during the pause and wrote `verify` — is what forced the continuation to exist. A human can also explicitly declare `continue`, `mark_complete` (finished the goal manually), or `abandon`, covering cases checkpoint verification alone can't resolve. The human's turn is recorded passively — a screenshot and observation snapshot at pause and at resume, plus the navigation trail in between — a real but intentionally coarse record (state changes, not click-by-click input capture).

## 6. Safety

**Allowlist.** Two dimensions, both declarative config: a domain/route allowlist checked at every `navigate`, and an action-type/capability permission set checked at every tool call. Both are enforced at points the system already fully controls (every action is a typed tool call), not inferred from page content. Both dimensions also grew teeth from live incidents: routes can be *denied* ahead of any allow rule (`denied_routes` — ParaBank's admin page hosts destructive Initialize/Clean/Shutdown controls inside an otherwise-allowed route space, and a goal-blocked run navigated there and wiped the database before this existed), and **link clicks are navigations**: the adapter records every anchor's absolute `href` and the `click` tool checks it against the same allowlist before executing — that run reached the admin page by *clicking a link*, which a `navigate`-only check cannot see. (Replay-side clicks remain trusted-by-review — a different trust model: artifacts are reviewed, risk-tagged and confirmation-gated before they ever run.)

**Risk & irreversibility.** Risk is a property of what a *capability* accomplishes, not of individual clicks — a single `risk_level` tag per artifact (`read_only` / `reversible` / `irreversible`), set manually when the artifact is authored. An irreversible artifact additionally flags its specific point-of-no-return step; replay requires an explicit `confirm=True` argument from the caller before executing that step. This puts the conservative gate exactly where it matters (the point of no return) rather than needlessly restricting every action in a flow.

**No invented data.** The agent is instructed never to fabricate values the goal doesn't provide; a missing required value routes through `report_stuck` → intervention, and a human supplies it during the handoff. This is a model-judgment constraint, not a deterministic gate — deliberately, since a grounding check would be the fuzzy matching rejected elsewhere in this design — with every typed value and the model's one-sentence reasoning logged as the compensating control. The incident that prompted it (a run that invented a zip code and phone number to pass bill-pay validation) is preserved in the evidence, found precisely because that log exists.

**Data handling.** Credentials are read from environment/config at session start and never written to any log, artifact, or evidence file, full stop. Parameter and output fields whose declared name matches a sensitive pattern (password, SSN, account number, PIN, etc.) are masked before persistence — by the evidence writer itself, not by a later review pass — even though the live value is still used in-session to perform the action. One deliberate deviation, stated rather than hidden: the mask is toggle-gated and shipped **off** (`BANKOPS_REDACT=false`, `--redact` re-enables) by operator preference for the live demo runs, so the evidence in this repo contains unmasked ParaBank *demo* values; the masking machinery itself is implemented and covered by tests.

**Known limitation, stated plainly:** sensitive-field masking is name-pattern-based, which depends on descriptive field naming (already ensured by how inputs/outputs are auto-named) — a sensitive field with a genuinely non-obvious name could in principle be missed. This is a real gap, not a hidden one.

## 7. Cuts

Deliberately left out, with reasoning:

- **All-candidate locator evaluation (replay).** Only the first resolving candidate is used — though *which* tier won is always logged (Section 4's drift signal). Evaluating the remaining candidates to detect non-primary matches would give near-free secondary UI-drift visibility over time. Cut for simplicity given the time-box; a natural next step.
- **Recognized loading-indicator tolerance.** Designed (DECISIONS.md §6b) but not built; the tiered retry absorbs transient slowness generically instead.
- **Granular human-input capture during handoff.** Only before/after screenshots and a navigation trail are recorded, not click/keystroke-level events. Capturing that would need injecting page-level input listeners — a meaningfully larger lift for audit fidelity this project's scope didn't require.
- **Multi-tenant and desktop-surface support.** Designed for (Section 4) but not built, per the assignment's own explicit scope note.
- **A real operator notification channel and remote co-browsing console.** The intervention request and control-transfer mechanism are real; the *delivery* of the notification and the *remoteness* of the operator are both stubbed, since a full console is explicitly out of scope.
- **Confidence scoring / approval gating for artifacts (stretch goal).** Not attempted — the manual `risk_level` tagging step substitutes for this at current scale, with the trade-off (a human must remember to set it correctly) stated openly rather than hidden.

**What I'd build next with more time:** the all-candidate drift-logging upgrade (cheapest, highest-value next step), an author-time checklist or heuristic to make risk tagging less relevant on human memory, and a real second-tenant variant of one artifact to validate the override-diff design against an actual second surface rather than only against ParaBank.
