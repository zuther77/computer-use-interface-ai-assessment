# Design Decisions — Computer-Use Automation System

This is the rationale companion to `IMPLEMENTATION_PLAN.md`. The plan says *what* to build, in what order; this says *why*, so that any ambiguous edge case hit during implementation gets resolved consistently with the reasoning already worked through — not improvised fresh. If a coding agent is unsure how to handle something not explicitly covered by a phase's task description, the right move is to check whether the underlying rationale here settles it, and flag it back for a decision if it doesn't.

Decisions are numbered to match the step/sub-step structure they were made under. Nothing here should be silently overridden during implementation without flagging it back first.

---

## 1. Target surface

**Decision:** ParaBank, self-hosted via Docker (`parasoft/parabank`), not the public hosted instance.

**Why:** ParaBank gives a real banking domain (login, open account, transfer funds, bill pay, find transactions) with native, non-simulated business-outcome errors (insufficient funds, invalid login, not-found lookups) — satisfying the error-taxonomy requirement without needing to fake conditions. It's legacy-*ish* (server-rendered JSP, table layouts) but not adversarially hostile, which is an acceptable trade given the rubric weights the artifact schema and replay/error-handling far more than "how ugly was the DOM." The public hosted instance was ruled out specifically because its database is reported to reset frequently and it's shared with unrelated QA traffic — a real reproducibility risk for evidence that needs to still work when reviewed later. Local Docker removes that risk entirely and carries no ToS concern, since Parasoft built and ships the image for exactly this purpose.

## 2. Core stack

**2. Language/runtime — Python.** Chosen for comfort/familiarity (explicit user preference) and because it has equally strong Playwright support and Pydantic for runtime-validated typed schemas, which the artifact contract depends on throughout.

**2b. Perception mechanism — Hybrid.** DOM/role-based Playwright locators are the primary signal for both discovery and replay; screenshots are captured at every step purely as an evidence/debug artifact, never as a decision input. Chosen because DOM/role-based targeting gives the determinism and locator-robustness story the rubric weights heavily, while screenshots still satisfy the observability requirement (3.5) and leave a natural, low-cost story for extending toward more hostile or desktop surfaces later (swap the perception adapter, keep the artifact schema — see Decision 11a).

**2c. Automation library — Playwright (Python).** Native role-based locators (`get_by_role`, etc.) map directly onto the chosen perception strategy; built-in auto-waiting reduces flaky-wait boilerplate; handles full-page JSP navigation without special-casing. Selenium was ruled out for lacking built-in auto-wait (more boilerplate, weaker "determinism" story); a screenshot/coordinate-based "computer use" SDK was ruled out as it would have undermined the DOM-first decision in 2b.

**2d. LLM provider — GLM-5.2, via the OpenAI Python SDK (configurable `base_url`/`api_key`).** Driven by an explicit cost constraint (no willingness to spend on premium-tier tokens) balanced against the one property this task needs most: reliable structured tool-calling in an iterative agent loop. DeepSeek was evaluated and ruled out — an agent-framework's own documentation reports DeepSeek's function-calling as unstable specifically in agentic tool-use loops (looped calls, empty responses), which is the exact failure mode this system can least tolerate, since one malformed action can silently corrupt a recording. GLM-5.2 was chosen over Qwen3.5 on the strength of published agentic/tool-use benchmark results and independent reports specifically praising its function-calling reliability (correct function names, correct parameter types) — directly the property DeepSeek was weak on. Using the OpenAI SDK (rather than a native GLM SDK) means the tool-schema contract is written once against the OpenAI tool-calling spec, making a future provider swap a `base_url`/`api_key` change, not a rewrite.

## 3. Discovery agent loop

**3a. Observation representation — Indexed interactive-element list, built on Playwright's accessibility snapshot.** A custom serializer emits a compact numbered list of interactive elements (`[3] textbox "Username"`) rather than raw HTML or the raw accessibility tree. Raw HTML was ruled out as token-expensive and prone to producing fragile, inconsistent locators when the model has to invent a selector by eyeballing markup. The raw accessibility snapshot alone was ruled out as still noisy on deeply nested tables and lacking a cheap stable reference the model can point back to. The indexed-list approach is cheapest token-wise, sharply reduces hallucination risk (the model picks from a closed set), and is the natural place to attach multiple candidate locators per element — directly feeding the fallback-locator design in Decision 4b.

**3b. Action emission — One typed tool per action type** (`click`, `type_text`, `select_option`, `navigate`, `extract`, `remember`, `finish`, `report_stuck`), each with parameters scoped to exactly what it needs. A single generic `act()` tool was ruled out for allowing structurally-valid-but-semantically-nonsensical calls. Raw code generation was ruled out outright — it's incompatible with a closed, auditable action space, which the allowlist (Decision 8a) depends on. Explicit `finish`/`report_stuck` tools give a clean, structured way to end a run instead of parsing free text for intent.

**3c. Context management — Structured running state, not transcript replay.** Each step gets the *current* observation plus a full compact action-history log plus an explicit `remember(key, value)` working-memory tool — no resending of prior full observations. Full transcript replay was ruled out for growing cost quadratically with run length, directly undermining the cost constraint behind Decision 2d. A sliding window was considered but rejected in favor of explicit memory because it doesn't solve long-range recall (a value read at step 2, needed at step 15) as cleanly, and the `remember` pattern happens to double as a natural precursor to the artifact's output-extraction design (Decision 4d).

**3d. Stopping conditions — Layered: max-step ceiling + no-progress detection (repeated observation/element-set or repeated failed action) + explicit typed self-report via `finish`/`report_stuck`.** A single blunt max-step cap was ruled out for giving no principled trigger for human escalation — "ran out of steps" is a poor signal to hand a human. Self-reported confidence scoring was ruled out as LLM confidence is notoriously uncalibrated. The layered approach reuses tools already built in 3b and produces a *typed reason* for stopping, which is exactly what the escalation trigger (Decision 9a) needs to carry to a human.

## 4. Artifact schema

**4a. Structure — Flat, linear ordered step list.** Mirrors what a single real discovery run actually produces; error/outcome handling is pushed into replay-time checks (Decisions 7a–7c), not encoded as artifact branches. A branching DAG was ruled out as requiring multiple discovery runs to populate (conflicting with the assignment's own framing that one run is sufficient) and adding complexity disproportionate to this project's scope.

**4b. Locator encoding — Ordered list of candidate locators per step, each tagged by strategy type** (`role_name`, `id_attribute`, `text_content`, `css_structural`, ...), tried in priority order at replay time until exactly one visible/enabled element resolves. A single locator string was ruled out for having no fallback path. A "race all candidates" approach was ruled out for reintroducing non-determinism into what must be a deterministic replay engine. This decision directly formalizes the fallback-locator groundwork already produced by Decision 3a.

**4c. Parameterization — Auto-promote `type_text`/`select_option` values into named input parameters** (name derived from the target element's accessible label), with an optional per-step `is_constant` override for the rare case auto-promotion is wrong. Manual-only parameterization was ruled out as contradicting the goal of a usable, automated record→replay pipeline. Pure auto-promotion with no override was rejected only because a small, optional escape hatch costs almost nothing and demonstrates awareness of the auto-promotion heuristic's limits.

**4d. Output mapping — `extract` actions become declared typed output fields** (name/type inferred from label/value shape); `remember` values stay internal working memory, never exposed to the caller. An implicit "dump everything remembered" approach was ruled out for not satisfying the "typed outputs and their shape" requirement (3.2) and for conflating scratch memory with actual deliverables. This decision depends on the discovery loop using `extract` deliberately for anything meant to be caller-facing — enforced via prompting ("use `extract` specifically for information the goal asked you to retrieve").

**4e. Checkpoints — Automatic per-step signature (post-step URL + a stable page-identity signal, captured passively during observation) plus one deliberate terminal checkpoint tied to the goal.** Implicit success (all steps ran without a locator failure) was ruled out as exactly the "assumed the click worked" mistake the glossary calls out — a step can execute while the page shows a validation error instead of progressing. A single terminal-only checkpoint was upgraded to include per-step signatures because the added data is already being captured as an observation byproduct, and it gives precise mid-flow failure localization (which step, what was expected, what was observed) rather than a confusing failure only surfaced at the end.

**4f. Serialization — Pydantic model as the canonical typed schema, serialized to plain JSON with a `schema_version` field.** YAML was considered but offers no functional advantage over pretty-printed JSON. A database record was ruled out as exactly the kind of "scaling infrastructure" the assignment says not to build at this scope; a file is also easier for a human reviewer to open directly. Git provides artifact version history; no separate versioning mechanism is needed.

## 5. Recording mechanism

**5a. Recording filter — Distill to the successful path only** (last-write-wins per target, abandoned branches dropped from the artifact but preserved in raw evidence logs). Recording everything verbatim was ruled out as directly contradicting the assignment's explicit instruction that the artifact be "decoupled from the raw model transcript" — verbatim recording would replay mistakes, not just the goal. Discarding any run with retries/corrections was ruled out as wasteful and unrealistic, given the environment is explicitly framed as one with real runtime conditions the model must navigate.

**5b. Pipeline shape — Two-phase: discovery loop produces a raw action log only; a separate post-processing pass applies 5a's filtering, then runs 4c/4d classification over the final clean sequence.** Inline classification during the run was ruled out as awkward given steps can be superseded/dropped later by 5a's filtering — classifying a value as a "final" input parameter before knowing if it survives filtering is premature work that would need undoing.

**5c. Artifact trigger — Strict: an artifact is only built when the loop ends via `finish`.** A more lenient trigger (also building partial artifacts from `report_stuck` runs) was ruled out as reintroducing the mandatory-manual-editing problem already avoided in 4c/4d, and — more importantly — as a real safety concern: a half-built capability sitting in the same store as real ones risks accidental production invocation.

## 6. Replay engine

**6a. Locator resolution — Try candidates in priority order, stop at first unique match; fail only if all candidates are exhausted.** An "evaluate every candidate and log non-primary matches" variant (which would give free UI-drift detection) was consciously **cut for simplicity** and documented as a future upgrade rather than built now — see `/REPORT.md` Cuts section.

**6b. Waiting/retry — Playwright's built-in auto-wait (element-level) plus an explicit tiered step-level retry with backoff for "locator not found yet," plus tolerance for a recognized loading indicator where observable.** Relying on auto-wait alone was ruled out for treating "still loading" and "genuinely stuck" identically (same generic timeout either way). A full custom polling loop replacing auto-wait entirely was ruled out as reinventing what Playwright already does well.

**6c. Parameter validation — Validate caller-supplied arguments against the artifact's Pydantic input model before any browser interaction begins.** Near-free given the schema is already Pydantic-based (Decision 4f); rejecting bad input at the boundary, before touching the live session, is both cheaper and cleaner to diagnose than letting a type mismatch surface as a confusing mid-flow UI failure several steps later.

**6d. Session lifecycle — One browser context per replay invocation; torn down on success/hard-failure/post-handoff, but kept alive specifically on the escalation exit path.** A long-lived, reused session pool was ruled out as introducing state-leakage risk between unrelated calls — a real correctness and safety concern for a regulated-data system — and as exactly the kind of scaling infrastructure the assignment discourages building prematurely. This decision exists specifically to make Decision 9b (handoff on the *same* live session) buildable without any pooling infrastructure.

## 7. Error/outcome taxonomy

**7a. Step-level classification — Recorded outcome signatures.** Each step's checkpoint can carry additional "known alternate outcome" signatures (locator + expected text pattern), each tagged `business_outcome` / `recoverable` / `hard_failure` at recording time — captured via a **deliberate secondary discovery run**, not inferred generically. A purely locator-based success/failure rule was ruled out as reproducing the exact conflation the assignment's glossary calls "the most common design mistake." A generic pattern-library approach (detecting error-styled banners heuristically across any artifact) was ruled out as reintroducing the fuzzy, non-deterministic detection the whole locator-strategy design was built to avoid.

> **Action required, not yet done:** after the main successful discovery run produces an artifact, run a second, short, targeted discovery/exploration pass against ParaBank to deliberately trigger one native business-outcome condition on a step that already exists in the artifact (e.g., an over-limit transfer to trigger insufficient-funds; a nonexistent account ID to trigger not-found). Capture that outcome's locator + text pattern using the same observation/indexing mechanism already built (Decision 3a), then manually merge the signature into the corresponding step of the saved artifact JSON with the correct classification tag. This run doubles as the required `/evidence/replay_error_*/` deliverable — it is not optional polish.

**7b. Run-level rollup — First non-success classification short-circuits the run immediately; recoverable conditions are handled inline and don't terminate.** Continuing to execute remaining steps after a business-outcome or hard-failure detection was ruled out on safety grounds, not just complexity — acting on a page in a state the artifact was never designed for risks doing something unintended on a live financial-data system.

**7c. Result shape — Discriminated union of typed Pydantic result models** (`SuccessResult`, `BusinessOutcomeResult`, `FailureResult`), each carrying only the fields relevant to that outcome. A single flat result with a generic `details` dict was ruled out as reintroducing the same untyped-ambiguity problem already avoided for outputs in Decision 4d.

## 8. Safety & guardrails

**8a. Allowlist model — Two-dimensional: domain/route allowlist checked at `navigate`, plus an action-type/capability permission set checked at every tool call.** A domain-only allowlist was ruled out for saying nothing about *what* the agent can do once on an allowed domain — it satisfies only half of the assignment's own wording ("permitted domains/routes, **and** which action types are allowed"). Arbitrary policy code was ruled out in favor of a declarative, reviewable config structure.

**8b. Risk classification — Per-artifact risk tag** (`read_only` / `state_changing_reversible` / `state_changing_irreversible`), **set manually at authoring time**; irreversible artifacts additionally flag their point-of-no-return step, and replay requires an explicit `confirm=True` argument before executing that step. Classifying risk by action *type* alone was ruled out as unable to distinguish a harmless click from a dangerous one — risk lives in what a capability accomplishes, not in the mechanics of a click. Runtime heuristic detection (guessing danger from button text) was ruled out for the same fuzzy-matching reasons rejected elsewhere.

> **Action required, not yet done:** for every artifact produced, manually set its `risk_level` field based on what the capability actually does, and for any irreversible artifact, manually flag its point-of-no-return step. This is a known manual step at this project's scale — document it as such in `/REPORT.md` (Safety and/or Cuts sections); a production system would need author-time prompting or a reviewer-approval flow instead of relying on this being remembered correctly each time.

**8c. Redaction — Field-level redaction by design.** Credentials are read from environment/config at session start and never written to any log, artifact, or evidence file. Parameter/output fields whose declared name matches a sensitive pattern (`password`, `ssn`, `account_number`, `pin`, etc.) are masked before persistence, even though the live value is still used in-session to perform the action. Screenshots are scoped to the action-relevant viewport where feasible. Manual post-hoc redaction was ruled out as treating "never persist" as a promise rather than an enforced property. Encryption-at-rest was ruled out as not actually satisfying "never persist raw sensitive data" (it shifts risk to key management) and as unnecessary infrastructure at this scope. **Known limitation, stated honestly rather than hidden:** pattern-based masking depends on descriptive field naming (already ensured by Decisions 4c/4d) and could in principle miss a sensitive field with a non-obvious name.

## 9. Escalation & handoff

**9a. Intervention request — Structured `InterventionRequest` Pydantic model** (run_id, source, goal/artifact reference, step_index, reason, screenshot_path, observation snapshot, timestamp), persisted to `/pending_interventions/{id}.json` the moment it's raised. Notification itself (how a human is alerted) is stubbed as a log/alert, since routing infrastructure is out of scope — but the request object itself is real and complete, not a placeholder. A bare log line was ruled out as failing to satisfy the assignment's explicit requirement that the request carry enough context to act on.

**9b. Control-transfer mechanism — Headed (non-headless) local browser.** On escalation, the automation loop stops issuing commands entirely and blocks on a resume signal (CLI/file/stdin), while a human operates the same visible Playwright-controlled window directly. The "operator console" is the raw browser window itself — bare but real, matching the assignment's own scope note ("even a bare/mock operator surface"). A fully simulated handoff (describing what a human would do, without a real mechanism) was ruled out outright — the assignment explicitly states the handoff mechanism itself must be real, not just designed. Remote/co-browsing was ruled out as explicitly out of scope; it's documented in `/REPORT.md` as the natural production-scale next step instead.

**9c. Resume mechanism — Re-observe and verify by default, plus an explicit human-declared override.** On resume, automation takes a fresh observation; for a replay resume, it checks the next step's expected checkpoint against the current state — a mismatch raises a *new* intervention rather than guessing; for a discovery resume, the loop simply continues its normal per-step cycle from the new state (near-free, since this is what it already does every step). A human can also explicitly declare `continue` / `mark_complete` (goal already achieved manually) / `abandon`, for cases checkpoint-matching alone can't resolve. Blind resume (assume the human left the page exactly where the next step expects) was ruled out as risky and unverified — specifically dangerous when combined with an irreversible-class capability (Decision 8b).

**9d. Human-action recording — Passive before/after capture**: a screenshot and observation snapshot taken at pause and at resume, plus a navigation/URL trail during the human's turn, reusing existing screenshot/evidence machinery. Full input-event-level capture (injecting JS listeners to record every click/keystroke) was ruled out as disproportionate implementation complexity for a take-home whose rubric doesn't require that fidelity — documented as a known limitation and a natural future upgrade, not a silent gap.

## 10. Evidence & observability

**10a. Structured logs — JSONL, one typed `StepLogEntry` record per step** (action taken, locator used + which strategy tier won, observation summary, LLM reasoning, result classification, timestamp), appended incrementally. Free-form text logs were ruled out as failing the assignment's explicit "structured" wording and as inconsistent with the Pydantic-everywhere pattern used throughout. Appending per-line means a mid-run crash doesn't lose already-logged data.

**10b. `/evidence/` layout — One self-contained subfolder per run** (`discovery_run_{id}/`, `replay_success_{id}/`, `replay_error_{id}/`), plus a shared canonical artifact store. A flat dump of all files was ruled out as harder for a reviewer to navigate, working against the "Communication" rubric line. The per-run structure maps 1:1 onto the assignment's own listed required content.

## 11. Heterogeneity & multi-tenant design (write-up only — not built)

**11a. Surface abstraction — Formalize the existing seam as a `PerceptionAdapter` interface.** Observation (3a) and action execution (3b/6a) already only interact with the rest of the system through two shapes: "give me an indexed list of elements with candidate locators" and "execute this typed action against a locator." A legacy web adapter would implement the same interface with new locator-strategy tags (e.g. `table_cell_position`, `frame_scoped_xpath`); a desktop adapter would use OS accessibility APIs producing the same output shape (e.g. an `automation_id` tag). Crucially, the artifact schema, replay engine, and error taxonomy would all be entirely unaffected — they operate on the adapter's output shape, not on browser DOM specifics. This argument is credible specifically because it points at real decisions already locked, not at hypothetical future flexibility.

**11b. Multi-tenant reuse — Base artifact + sparse per-tenant override diff.** One canonical "base" artifact per capability; a per-tenant override is a small, optional diff replacing only specific fields (a locator candidate, a route segment, a label string) — not a parallel artifact. Drift detection reuses data already logged for free: `StepLogEntry` (Decision 10a) already records which locator-strategy tier resolved each step; a tenant whose replays start falling back to lower-priority strategies (or failing) at a materially higher rate than others is a concrete, measurable drift signal with no new instrumentation. **Explicit boundary case, stated honestly:** a tenant whose customization is too large to represent as a small override should get a newly-recorded base artifact instead of a forced-fit diff — re-recording is the honest answer beyond a certain divergence, not a failure of the design.

## 12. Repository structure

Package layout mirrors Steps 3–10 module-for-module (see `IMPLEMENTATION_PLAN.md` for the full tree), so that a reviewer can trace any design decision above directly to the file that implements it. `/evidence/` follows the per-run layout from Decision 10b. `/config/` holds the allowlist (8a) and provider settings (2d) as plain, reviewable files rather than code.
